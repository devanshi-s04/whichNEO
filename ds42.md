# ds42 on L01 — running log

Why this exists, what we have found, and what is still open. This is the
**research log**; `deploy/DS42.md` is the operations runbook (how ds42 is
installed, how to update it, what identifies a score). Read that one before
touching the install; read this one before drawing a conclusion.

Goal: **a research note on initial results using ds42 for L01.** Everything
below is in service of that.

---

## What ds42 is, in one paragraph

`ds42` (Devanshi's Score 42, repo `mjuric/digest42`) is a Bayesian NEO
tracklet classifier. Given one tracklet it returns a **calibrated posterior
probability** that the object is an NEO. digest2 — what the board sorts on
today — returns a heuristic 0–100 score. The intent is to run both, show
`p_neo` beside the digest2 score, and bank the results so the two can be
compared once objects resolve.

**whichNEO still does not import ds42.** It runs as a **subprocess** from its
own virtualenv, so its dependencies stay its own and a failure — a missing
install, a broken model, a segfault in the Rust kernel — is an exit code to
handle rather than a dead updater. The board's job is telling an observer
where to point a telescope; a research score is not worth risking that.

### Why stage 3 collapsed into stage 2

The original plan had scoring and history as separate steps, with scores
first living somewhere convenient and then being copied into an append-only
store. There is no useful intermediate: `targets` is rewritten every cycle
and `prune_cache` drops an object the moment it leaves NEOCP — which is
exactly when its score becomes interesting, because that is when we can
finally ask whether ds42 was right. So the scores went straight into their
own `ds42_scores` table, written once per object and never updated, with the
provenance columns alongside.

Scoring is one-shot because p_neo is one-shot: it is a function of the
discovery tracklet and does not move (finding 1). A second pass over the
same objects costs 0.00 s, because nothing is left to do.

Install lives at `/home/devanshi-s04/ds42` — outside this repo, because ds42
is a separate fast-moving project and vendoring it would fork someone else's
work.

## The run archive

`/home/devanshi-s04/ds42/runs/<night>/` — one directory per **night label**,
not per calendar day the script ran. (The first run was banked under
`2026-09-16` while holding night `2026-09-15`; renamed, but worth knowing if
an older reference turns up.)

Each holds `scores.tsv`, `neocp_astrometry.obs` (the raw 80-column records),
`meta.json` (the board's own view: digest2 score, V, nobs, observability),
`score.err`, the two scripts used, and `provenance.json`.

`provenance.json` records what `deploy/DS42.md` says a score needs to mean
anything: ds42 git HEAD **resolved at scoring time** (never
`ds42.__version__` — an editable install freezes that string), a dirty flag,
the model's sha256, the whichNEO HEAD, and the full configuration.

Cost of keeping everything: **~62 KB per night, ~12 MB per 200-night
season.**

## Findings

### 1. p_neo does not move as follow-up accumulates

**This is the important one.** Of 60 objects present on both banked nights,
**all 60 have an identical p_neo**, and 17 of them gained observations
overnight:

| target | NEOCP obs | ds42 used | p_neo |
|---|---|---|---|
| AFS700 | 6 → 14 | 3 → 3 | 0.8785 → 0.8785 |
| C46K1R1 | 141 → 157 | 8 → 8 | 0.9968 → 0.9968 |
| P12qfu9 | 3 → 8 | 3 → 3 | 1 → 1 |

ds42 scores the **discovery tracklet** — the CLI defaults truncate to the
first 2 hours of the first night (`--max-arc-hours 2`, `--night-gap-hours
3`). Everything L01 observes afterwards changes nothing.

Consequences, all of which have to be decided before Stage 4:

- A `p_neo` column beside digest2 shows a number that **never changes while
  its neighbour does**. An observer would reasonably conclude it is broken.
  Settled: the column is labelled as a discovery-tracklet score and the
  header explains it on hover -- see **Decided** below.
- "Does ds42 do better than digest2?" can currently only be asked **at the
  discovery tracklet**. That is a real and defensible question, but it is
  not the question "which should the board sort on tonight".
- Raising `--max-arc-hours` would let it use more of the arc, but the model
  is calibrated for tracklets. That is a scientific decision for Mario, not
  a configuration tweak.

### 2. digest2 saturates; ds42 discriminates

Both nights, roughly 40–44 of ~72 scored objects sit at **digest2 = 100**.
ds42 spreads those same objects across **p_neo 0.003 – 1.000**.

Our own `MIN_SCORE = 25` cut kept **71 of 71** scored objects on 2026-09-16.
It is doing no filtering at all at the top of the list.

Concrete: on 2026-09-16, **P12pWTl** was on the observable board at digest2
77 and **p_neo 0.064**. Going the other way, **P22pL41** scored digest2 73
and **p_neo 0.993** but is excluded as `TOO_FAINT` at V 21.8 — a telescope
limit, not a scoring question, but the shape of miss worth tracking.

### 3. NEOCP is destructive — 22% attrition in one night

77 objects on 2026-09-15, 73 on 2026-09-16: **17 gone, 13 new, 60 carried
over.** Objects roll off as they are designated or rejected, and
`showobsorbs.cgi` stops serving them.

**A night not captured cannot be reconstructed later.** That is the argument
for automating capture rather than running a script by hand.

### 4. A ZTF cluster returns `empty_region`

2026-09-15: ZTF10Fv, Fx, Fy, G2, G9. 2026-09-16: G2, G9 (the other three
left NEOCP). All had nobs = 4 and digest2 = 100.

`empty_region` means no bound orbit is consistent with the attributable at
all, so `p_neo` is undefined (nan). The same ZTF-specific failure appeared in
the earlier pilot, so it is a **pattern, not noise**. Needs understanding
before publishing — it could be a rate-fit or obscode issue specific to how
ZTF submits, rather than a genuine astrophysical verdict.

### 5. Known selection effect

**49 of 122 targets are cheap-rejected before any astrometry is fetched** —
25 `NOT_SEEN`, 16 `NOT_NEO`, 6 both, 2 `SHORT_ARC`. Those never reach ds42.

So any comparison covers only what the board already takes seriously. This
belongs in the research note's methods, not in a referee's first reply.

### 6. Tracklet versus arc is not a like-for-like comparison

ds42 scores one tracklet; digest2 scores everything submitted. A11FPxB was
52 observations for us and **4** for ds42; C46K1R1 was 141 and **8**. For
fresh discoveries they are comparable. For long arcs the comparison is
currently unfair to ds42, and any headline number has to say which
population it covers.

## The column, as built

`ds42`, between Score and V, sortable like every other column. Three states,
kept deliberately distinct:

| shown | means |
|---|---|
| `0.064` | a posterior. Hover for the full value and how many observations it used |
| `—` | scored, but no posterior — hover says why (`empty_region`) |
| `·` | never scored. Cheap-rejected objects never have astrometry fetched, so ds42 never sees them |

Collapsing the last two would hide whether ds42 has an opinion or has simply
not looked, and **49 of 122 rows are in that third state** — it is not a rare
case.

Uncoloured on purpose. Whether a low `p_neo` should discourage observing is
exactly the question this column exists to investigate; the board should not
answer it by implication before we have the evidence.

Sorting ascending is the useful view: it puts the disagreements at the top.
On 2026-09-16 that was P12pWTl at **digest2 77 / p_neo 0.064**, then P22qfOa
at **digest2 100 / p_neo 0.306**.

## Decided

**The column says what it is.** The `p_neo` column is labelled as a
discovery-tracklet score, and hovering the column header explains that:
it is scored from the discovery tracklet, so unlike the digest2 score beside
it, it does not change as follow-up accumulates.

That is the honest framing rather than a workaround. A frozen number beside
a moving one reads as a bug; a number that says "this is what the discovery
tracklet implied" reads as a different measurement, which is what it is.
Requirement for Stage 4: the header carries a `title` explaining this, in
the same way the Shoot, Alt and Az headers already do.

## Reference

- Measured performance: rust backend **25.4 ms/tracklet** vs python 357.7 ms,
  agreeing to **6.11e-16** on p_neo. Full-night scoring is ~5 s for ~75
  objects.
- Configuration that must be pinned, and why, is in `deploy/DS42.md`. The two
  that change answers materially: `variant="All"` and `h_extend_to=30.0`.
- `status="fully_truncated_flagged"` returns `p_neo = 1.0` **assigned by
  triage policy**, not computed. Same number as a genuine posterior, a
  different claim. Neither banked night has produced one, but it must be
  shown distinctly and kept out of any calibration statistic.
