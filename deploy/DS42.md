# ds42 — install, update, and why each step is the way it is

`ds42` is a Bayesian NEO tracklet classifier — given one tracklet it returns a
**calibrated posterior probability** that the object is an NEO, where digest2
returns a heuristic 0–100 score. We intend to run it alongside digest2, show
`p_neo` as a column, and bank the results so the two can be compared once
objects resolve.

This document records **Stage 0 only**: getting ds42 installed and verified on
epyc. Nothing in whichNEO calls it yet.

Repository: `mjuric/digest42` (private; being renamed to `mjuric/ds42` —
GitHub will redirect, but update the remote when it lands).

---

## Layout

```
/home/devanshi-s04/ds42/
├── src/      the checkout (git)
├── venv/     12 MB, --system-site-packages
└── data/     model + observatory codes, ~4.3 MB
```

Deliberately **outside** the whichNEO repo. ds42 is a separate, fast-moving
project; vendoring or submoduling it would fork someone else's work and drift
the moment they change it.

## Install, as performed

```bash
mkdir -p /home/devanshi-s04/ds42
cd /home/devanshi-s04/ds42

gh repo clone mjuric/digest42 src          # private; needs gh auth

python3 -m venv --system-site-packages venv
./venv/bin/pip install -e src

cd src && ./rust/build.sh && cd ..         # optional but wanted; see below

mkdir -p data && ./venv/bin/ds42 fetch-model
./venv/bin/ds42 fetch-obscodes
```

### Why `--system-site-packages`

ds42 needs only `numpy>=1.24`, `astropy>=5.3`, `matplotlib>=3.7`. The host
already has numpy 2.3.5, astropy 7.2.0 and matplotlib 3.10.8 — the same ones
whichNEO uses. Inheriting them gives a **12 MB** venv instead of the **250 MB**
a fresh one produced during the pilot.

matplotlib is imported *lazily* (diagnostics only), so it never loads during
scoring.

### Why build the Rust kernel

Measured on this host, 25 real NEOCP tracklets:

| backend | per tracklet | total |
|---|---|---|
| rust | **25.4 ms** | 0.64 s |
| python | 357.7 ms | 8.94 s |

**14× faster.** And the two agree to **6.11e-16** on `p_neo`, with identical
statuses — better than the ~1e-13 the project's own docs claim.

The build took **38 s** (cargo 1.93.1, rustc 1.93.1). After it,
`backend.resolve_backend("auto")` returns `"rust"` on its own; nothing needs
configuring.

### Why the observatory-code file matters

The built-in table is 14 codes. `ds42 fetch-obscodes` writes 2693 with parallax
constants. On ds42's own 499-object validation, running *without* a full table
put 21% of tracklets at the geocentre, moving `p_neo` by up to **0.17** — worst
for survey stations like F52, which discovers a large share of what we see.

Our own `mpcdata/ObsCodes.htm` is a **different file** in a different format
and cannot be substituted.

Verified on our 67-object sample: **49 tracklets resolved from the file, 18
from the built-in table, 0 failures.**

## Updating

`git pull` alone is **not** sufficient, for two independent reasons.

```bash
cd /home/devanshi-s04/ds42/src
git pull
../venv/bin/pip install -e .       # refreshes the frozen version metadata
./rust/build.sh                    # REQUIRED if the extension is built
```

**`git pull` does not rebuild `_core.abi3.so`.** Pull anything touching
`rust/` without rebuilding and you are running a stale kernel against new
Python, silently and with no error.

**Editable installs freeze the version string at install time.** Ours currently
reports:

```
ds42.__version__   0.0.1.dev45+unknown.ga4bc84834
git rev-parse HEAD a4bc848347aa5e4c771d41fb365d056bd935db9c
```

These agree *today*. They will not after the next `git pull` without a
reinstall — the version keeps naming the old commit. On the ds42 maintainer's
own machine this drift is already present.

**Therefore: never identify a score by `ds42.__version__`.** See below.

## Provenance — what identifies a score

A stored `p_neo` is meaningless without knowing what produced it. Record all
of:

| field | how |
|---|---|
| code revision | `git -C /home/devanshi-s04/ds42/src rev-parse HEAD` **at scoring time** |
| dirty flag | `git status --porcelain` non-empty |
| model sha256 | hash the file actually passed — not `fetch_model.KNOWN_SHA256`, which is what the code *expects*; the fetcher warns but still writes on mismatch |
| configuration | `variant`, `h_extend_to`, `h_interpolation`, `h_top_bin_infinite`, grid, rho bounds, `G`, resolved backend |

Current values on this install:

```
code revision  a4bc848347aa (clean)
model sha256   2b9d9d2a6d8ab16d...
variant        All
h_extend_to    30.0
totals         742145.0 / 14868899.0     (NEO / other, post-parse cross-check)
```

Those totals are a cheap way to confirm the parsed model is the one you think
it is.

Do **not** depend on `backend._fingerprint()` — private, not in `__all__`, and
its composition changes when caching needs change.

Backend identity is worth recording but should not force invalidation on its
own: rust and python agree to 6e-16.

## Configuration to pin explicitly

Take none of these as defaults — pin them, because two change the answer
materially:

```python
Digest2Histogram.neo_other_pair(MODEL, variant="All", h_extend_to=30.0)
# grid: 1200 x 50 (the default, and what everything was validated at)
```

**`variant="All"`**, not `"Unk"`. Measured better on the real-NEOCP pilot
(ΔAUC +0.0104 [+0.0039, +0.0187]); `Unk` subtracts a known-object catalogue
frozen at 2011 and inflates `p_neo` for belt-like tracklets.

**`h_extend_to=30.0`** is the one that matters most. Without it, a tracklet
whose entire admissible region implies H > 25.5 falls outside the model and
scores 0/0. On the 499-object pilot that was 11 tracklets — **all 11 true
NEOs**, the fast faint close objects the NEOCP exists for.

A coarser grid moves `p_neo` by ~1e-2 in the mid-range.

## Reading a result

`res.p_neo` alone is not enough. Always read `res.status`:

| status | meaning |
|---|---|
| `ok` | a genuine likelihood-based posterior |
| `fully_truncated_flagged` | `p_neo = 1.0` **assigned by triage policy**, `log_lr = nan`, `policy_assigned is True`. **Not a posterior.** Must be shown distinctly and excluded from any calibration statistic; may legitimately appear in ranking statistics, since the policy is a claim about rank |
| `empty_region` | `nan` — no bound orbit is consistent with the attributable at all |
| `both_zero` | `nan` — a zero reached by some other mechanism |

The two routes to `1.000` are different claims wearing the same number. With
`h_extend_to=30` the policy case is rare, but rare is not never.
